# QWASAR Boot, Build and Session Model

**Scope:** pre-frontend startup, multiple Void Desk installations, build flavours, rendering engines, standalone sessions, PC integration and optional virtualization.
**Status:** architecture contract. The selector, multi-instance installer, GRUB adapter, QWASAR Link and VirtualBox provider are planned; do not imply they already run.

## 1. Two selectors, two different jobs

QWASAR uses two distinct layers:

1. **Bootloader / OS selector** — selects a complete bootable operating system or root filesystem. On a compatible PC, an optional GRUB2 adapter may generate entries for complete OS installations.
2. **QWASAR Launch Selector** — starts after the firmware or host OS has booted. It selects an installed Void Desk instance, build flavour, renderer, user profile and session target.

GRUB cannot switch Pygame to LÖVE inside an already running OS. That is an application-launch decision and belongs to the QWASAR Launch Selector.

### Platform behaviour

| Host | Startup path | Bootloader integration |
|---|---|---|
| H700 / muOS | muOS app launcher → muxapp → QWASAR Launch Selector → selected engine | No GRUB. Never replace the muOS bootloader or alter boot/recovery |
| Linux PC x86-64 | Linux desktop/menu → QWASAR launcher → selected instance/engine/session | Optional GRUB2 adapter only for complete bootable OS images |
| Other handheld firmware | Firmware app/package adapter → QWASAR selector when supported | Firmware-specific; never assume GRUB |

The standard Void Desk .muxapp or PC .deb installer must not edit GRUB, EFI variables, firmware boot order or bootloader configuration.

## 2. Independent choices in the launch selector

These are separate axes, not one combined build name:

| Axis | Choices | Meaning |
|---|---|---|
| Installed instance | One or more named instances | Which isolated Void Desk installation to start |
| Build flavour | Full / Essential / Slim / Custom | Which official modules and assets are included in that installation |
| Renderer | Pygame / LÖVE today; Qt 6 / LVGL / Web reserved | Which engine renders the selected UI manifest |
| User profile | Default or custom QWASAR profile | Layout, menu, widgets, theme and feature activation |
| Session target | Desktop / Terminal / PC workstation / VM | Which environment to enter after Void Desk is ready |

The selector remembers the previous valid selection but displays only combinations supported by the installed instance, frontend adapter, platform adapter and device capabilities. If an engine is missing or fails health checks, it offers an explicit compatible fallback; it never reports a fallback as feature-equivalent without a parity declaration.

## 3. Build flavours and side-by-side installation

The package builder will produce separately identifiable flavours:

- **Full:** all official first-party modules and supported integration assets for the target platform.
- **Essential:** shell, core services, essential tools and recovery; optional modules remain installable through THE FORGE.
- **Slim:** minimal core footprint with a selected engine and required recovery/maintenance tools.
- **Custom:** a reproducible selection generated by AppBuilder/Release Composer after validating dependencies, permissions and compatibility.

A flavour is a package composition, not a renderer. A Full Pygame installation and an Essential LÖVE installation are separate valid choices.

### Multiple instances

The installation manager must support more than one installed Void Desk instance without file collisions:

- every instance has a stable, unique instance ID and package ID;
- executable roots, assets, runtimes, service sockets and temporary request/response files are isolated per instance;
- package adapters create distinct launch entries (muOS application directories or PC menu entries);
- user data is namespaced per instance by default;
- sharing settings/data is opt-in and uses versioned, validated migrations;
- removing one instance never removes another instance's files or shared dependencies that are still referenced;
- the local inventory is owned by the trusted installer and stored in the format described by schemas/qwasar-installations.schema.json.

An imported profile or community module cannot define install paths or arbitrary executable entrypoints.

## 4. GRUB2 adapter — PC only

The optional GRUB2 adapter is for advanced PC installations that boot separate OS images/root filesystems. It is not part of ordinary Void Desk app installation.

Required safeguards:

1. read and report the current boot setup before changes;
2. show the exact proposed entry and affected files;
3. create and verify a backup;
4. require explicit user confirmation;
5. apply only a bounded generated entry through the host's supported GRUB configuration workflow;
6. provide a rollback path and verify the resulting configuration;
7. never update firmware boot order or EFI variables without a separately designed, explicit workflow.

On H700/muOS, no bootloader changes are permitted. Multi-instance selection is handled after the normal muOS app launcher has opened Void Desk.

## 5. START SESSION — environment hand-off

START SESSION launches environments that live outside the normal Void Desk workspace.

### Desktop environments

- XFCE
- IceWM
- LXDE
- future registered environments through a session adapter

On H700 these run inside the optional Debian/Ubuntu image. On a PC, only a host session adapter that passes compatibility and permission checks may be shown.

### Standalone terminal sessions

- PTY shell session
- Python console / REPL
- future TUI sessions

A standalone session is distinct from the bounded in-app terminal panel in RT:TOOLBOX. It has a clear start, foreground/return hand-off, exit status and cleanup path.

### PC workstation

A paired PC session is opened through QWASAR Link. UPLINK owns pairing and trust; START SESSION offers the session entry once pairing is valid. Remote input, remote display, file transfer and telemetry are separate capabilities.

### Virtual machines

On a compatible PC host, START SESSION can list and launch registered VirtualBox VMs. THE FORGE owns installation and verification of the host dependencies; START SESSION owns VM selection and launch. On H700/muOS the local VirtualBox target is unavailable.

## 6. Input Leap and the easy PC integration

Input Leap is a software KVM: it shares a PC keyboard and mouse across connected machines. The project README states that the software must run on all machines participating in the input-sharing setup; the machine with the keyboard/mouse is configured as server and the other endpoints as clients. It is not a video or remote-desktop transport. Clipboard support has display-stack limitations, including Linux/Wayland.

QWASAR Link should offer a guided setup:

1. discover the PC host and the handheld/client endpoint;
2. check whether a compatible Input Leap binary exists for both;
3. choose server/client roles and screen names;
4. establish and verify pairing/trust;
5. show the keyboard/mouse route and current connection state;
6. provide start/stop, reconnect and uninstall/disable actions.

Do not assume an Input Leap build exists for every H700 firmware. If a supported client is unavailable, offer the QWASAR Link remote-input adapter when implemented. Do not fake success or imply that keyboard sharing includes video.

Reference: [Input Leap project README](https://github.com/input-leap/input-leap).

## 7. VirtualBox compatibility

VirtualBox is an optional hosted hypervisor for PC, not an H700 runtime. The initial target is Linux x86-64. Before exposing VM actions, QWASAR must detect:

- the supported VirtualBox host package and VBoxManage;
- kernel driver/module availability;
- hardware virtualization support and relevant firmware settings;
- available VM registrations and their state;
- storage/RAM availability and any lock or running-state conflict.

The Forge installs/verifies prerequisites; START SESSION lists and launches existing VMs. The UI should not create or alter VM disk images without a separate reviewed workflow.

Oracle VirtualBox 7.2 documentation lists Linux host package options for x86-64 distributions. Linux ARM64 is not listed in the supported Linux host package matrix. Windows ARM and Apple Silicon have separate limitations; none of these facts justify promising native VirtualBox support on the H700. See [Oracle's installation guide](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/installation.html) and [host/guest combinations](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/Introduction.html).

A handheld may access a VM running on a paired PC through a future QWASAR Link remote-display session. That is remote access to a PC-hosted VM, not local virtualization.

## 8. Ownership across QWASAR workspaces

| Workspace | Owns |
|---|---|
| START SESSION | Launch desktop, standalone terminal, paired PC workstation and PC VM targets |
| THE FORGE | Install/update/remove APT packages, Void Desk builds, modules, external tools, renderers and virtualization prerequisites |
| UPLINK | Online/network services, pairing, Tailscale, Syncthing, Input Leap/QWASAR Link connectivity |
| MEDIA VAULT | Audio/video players, Internet radio, IPTV/streaming, local library and playback sources |
| RT:TOOLBOX | Four sections: Everyday Tools; Files & Storage; System & Diagnostics; Developer & Terminal |
| SETTINGS | Themes, controls, layout, renderer preference and shell composition |
| INFO / COMMUNITY | Manual, release notes, credits and community resources |
| END NODE | Safe exit and firmware/system hand-off |

QWASAR Inspector verifies the structure and QWASAR Switchboard controls activation at profile level. THE FORGE remains responsible for installation; disabling a feature in Switchboard is not an uninstall.
